2. KIẾN TRÚC TÍCH HỢP (DUAL-LAYER ON-CHAIN & OFF-CHAIN ARCHITECTURE)
--------------------------------------------------------------------------------
Hệ thống tuân thủ triệt để nguyên lý:
"Thư viện quản lý nghiệp vụ — Blockchain bảo chứng tính bất biến mật mã".

+------------------------------------------------------------------------------+
|                            FRONTEND (React 19 + Vite)                         |
|  - WalletContext: MetaMask provider, signer, network switch (31337)          |
|  - RegisterCopyrightModal: Parameter review, dual signing (Direct / Relay)   |
|  - Verify Page: Web Crypto SHA-256 file hashing, on-chain archival cert      |
+-----------------------+------------------------------+-----------------------+
                        |                              |
       Direct Contract  |                              | HTTP REST API
       RPC Calls (Ethers)|                             | (session cookie auth)
                        v                              v
+-------------------------------+      +---------------------------------------+
|  BLOCKCHAIN (Hardhat 31337)   |      |        BACKEND (Express.js)           |
|  Contract: 0x5FbDB...0aa3     |      |  - copyrightController & Service     |
|  - registerCopyright()        |<-----+  - contractClient (Ethers v6 Provider)|
|  - getCopyright(recordId)     |      |  - copyrightRepository (mssql pool)   |
|  - verifyHash(contentHash)    |      +-------------------+-------------------+
|  - totalRecords()             |                          |
+-------------------------------+                          |
                                                           v
                                       +---------------------------------------+
                                       |      DATABASE (SQL Server 2025)       |
                                       |  - dbo.Books & dbo.BookFiles          |
                                       |  - dbo.CopyrightRecords               |
                                       |  - dbo.BlockchainTransactions         |
                                       +---------------------------------------+

Các tham số mật mã được ánh xạ chuẩn xác giữa hai hệ thống:
1. `recordId` (SQL Server UUID) <---> bytes32 (Solidity `keccak256(abi.encodePacked(...))`)
2. `contentHash` (SQL Server CHAR(64) hex) <---> bytes32 (Solidity `bytes32(0x...)`)
3. `authorWallet` (EVM Address `0x...`) <---> CHAR(42) / NVARCHAR(42) trong SQL Server.
4. `status` (ON_CHAIN / PENDING / REVERTED trong SQL) <---> Status.ACTIVE (0) trong Smart Contract.


3. LUỒNG ĐĂNG KÝ BẢN QUYỀN (COPYRIGHT REGISTRATION WORKFLOW)
--------------------------------------------------------------------------------
Luồng thực tế bao gồm 10 bước nghiêm ngặt:

Bước 1: Tác giả đăng nhập vào BookChain Library bằng tài khoản có vai trò Tác giả (Author).
Bước 2: Tác giả mở trang chi tiết sách (`/books/:id`) và chọn phiên bản sách cần đăng ký.
Bước 3: Tác giả nhấn "Kết nối ví MetaMask". Hệ thống kiểm tra Chain ID (phải là 31337).
        Nếu sai mạng, ví sẽ được tự động yêu cầu chuyển sang Hardhat Local.
Bước 4: Tác giả nhấn "Đăng ký bản quyền On-chain" trên bảng điều khiển Blockchain.
Bước 5: Frontend gọi API `POST /api/copyright/prepare` kèm `bookId` và `bookFileId`.
        Backend kiểm tra:
        - Quyền sở hữu của tác giả đối với tác phẩm (`dbo.BookAuthors`).
        - Tệp phiên bản sách tồn tại và có mã băm SHA-256 tính từ chuỗi byte thật.
        - Kiểm tra xem phiên bản này hoặc mã băm này đã được đăng ký on-chain chưa.
        - Tạo bản ghi trạng thái `PENDING` trong `dbo.CopyrightRecords` và mã `RecordNumber`
          tuần tự định dạng `BCR-YYYYMMDD-XXXX`.
Bước 6: Giao diện hiển thị Modal xác nhận với đầy đủ thông tin minh bạch:
        - Tên tác phẩm, số phiên bản, dung lượng tệp.
        - Mã băm SHA-256 chuẩn mật mã (64 ký tự hex).
        - Địa chỉ ví tác giả hưởng quyền (`authorWallet`).
        - Địa chỉ ví thực hiện ký giao dịch.
        - Địa chỉ hợp đồng Smart Contract mục tiêu.
Bước 7: Kiểm tra quyền hạn `REGISTRAR_ROLE`:
        - Trường hợp A (Ví tác giả có `REGISTRAR_ROLE` - ví dụ Account #0):
          Frontend yêu cầu người dùng ký trực tiếp qua MetaMask gọi `contract.registerCopyright(...)`.
        - Trường hợp B (Ví tác giả là tài khoản cá nhân thông thường - ví dụ Account #1):
          Hệ thống giải thích rõ ràng và cung cấp tùy chọn "Ủy quyền qua Registrar Relay".
          Backend sử dụng ví Registrar có thẩm quyền để ký và phát giao dịch, đảm bảo `authorWallet`
          on-chain vẫn lưu chính xác là địa chỉ ví của tác giả.
Bước 8: Theo dõi biên lai giao dịch on-chain:
        Giao dịch được phát lên Hardhat Local. Hệ thống chờ biên lai `tx.wait(1)`.
Bước 9: Đồng bộ vào SQL Server:
        Frontend gọi `POST /api/copyright/sync` (hoặc Relay service tự động đồng bộ):
        - Đọc lại dữ liệu on-chain bằng `getCopyright(recordId)` để đối soát tính toàn vẹn.
        - Cập nhật `dbo.CopyrightRecords` thành `ON_CHAIN`, lưu `BlockNumber`, `ConfirmedAt`.
        - Cập nhật `dbo.BlockchainTransactions` thành `CONFIRMED`, lưu `GasUsed`, `BlockTimestamp`.
Bước 10: Modal hiển thị Chứng nhận đăng ký bản quyền thành công với Record ID, Transaction Hash,
         Block Number và liên kết mở nhanh trang Tra cứu xác minh.


4. LUỒNG XÁC MINH BẢN QUYỀN (COPYRIGHT VERIFICATION WORKFLOW)
--------------------------------------------------------------------------------
Trang Xác minh (`/verify`) được thiết kế công khai cho độc giả, nhà xuất bản và cơ quan quản lý:

1. Chế độ Xác minh qua Tệp (Upload File Verification):
   - Người dùng kéo thả hoặc tải lên tệp PDF/EPUB của cuốn sách.
   - Trình duyệt sử dụng Web Crypto API (`crypto.subtle.digest('SHA-256', arrayBuffer)`)
     để tính mã băm mật mã trực tiếp tại máy client. Tuyệt đối không tải nội dung tệp lên server.
   - Gửi mã băm vừa tính đến API `GET /api/copyright/verify?hash=0x...`.

2. Chế độ Tra cứu trực tiếp (Hash / RecordId / Query Search):
   - Người dùng nhập trực tiếp chuỗi băm 64 ký tự hex hoặc mã định danh bản ghi UUID.
   - Hỗ trợ tham số URL dạng `/verify/:query` hoặc `/verify?q=...` để nhúng vào QR Code.

3. Quy trình xác thực On-chain:
   - Backend gọi hàm `verifyHash(bytes32)` và `getCopyright(bytes32)` trực tiếp trên Smart Contract.
   - Kết quả trả về gồm:
     * Tồn tại trên blockchain hay không (`exists`).
     * Trạng thái bản quyền (`ACTIVE`, `DISPUTED`, `REVOKED`).
     * Mốc thời gian ghi nhận khối (`registeredAt`).
     * Địa chỉ ví tác giả sở hữu (`authorWallet`).
     * Địa chỉ ví đăng ký viên (`registrant`).
     * Thông tin đối chiếu trong cơ sở dữ liệu thư viện (Tên sách, tác giả, phiên bản).

4. Trình bày Giấy chứng nhận số (Archival Certificate):
   - Nếu bản ghi hợp lệ: Hiển thị chứng chỉ trang trọng với con dấu xanh "VERIFIED ON-CHAIN",
     thẻ trạng thái hiệu lực, thời gian khối, địa chỉ ví tác giả rút gọn và mã giao dịch.
   - Nếu không tìm thấy: Hiển thị cảnh báo "KHÔNG TÌM THẤY BẢN QUYỀN TRÊN BLOCKCHAIN",
     kèm giải thích rõ ràng về việc tệp chưa đăng ký hoặc đã bị chỉnh sửa nội dung.


5. CƠ CHẾ ĐỒNG BỘ BLOCKCHAIN VÀ SQL SERVER (SYNC & FAULT TOLERANCE)
--------------------------------------------------------------------------------
Do Blockchain và SQL Server là hai hệ thống phân tán không có giao dịch nguyên tử (ACID chung),
hệ thống triển khai cơ chế đồng bộ lũy kế (Idempotent Sync) và chống xung đột:

1. Trạng thái giao dịch 2 pha (Two-phase State Tracking):
   - Pha 1: `PENDING` — Khi yêu cầu được tạo, SQL Server ghi nhận giao dịch đang xử lý.
   - Pha 2: `ON_CHAIN` / `CONFIRMED` — Chỉ được chuyển sang trạng thái này sau khi
     hàm `provider.getTransactionReceipt(txHash)` xác nhận `status === 1` và
     hàm `contract.getCopyright(recordId)` đọc thành công dữ liệu từ Smart Contract.

2. Tính lũy kế (Idempotency):
   - API `POST /api/copyright/sync` có thể được gọi nhiều lần cho cùng một `recordId` và `txHash`
     mà không tạo ra bản ghi thừa hoặc gây lỗi cơ sở dữ liệu.
   - Nếu bản ghi đã `ON_CHAIN`, hệ thống trả về ngay thông tin hiện tại kèm biên lai đối chiếu.

3. Xử lý lỗi lệch pha (Split-brain Recovery):
   - Nếu giao dịch on-chain đã thành công nhưng bước lưu SQL bị mất kết nối mạng hoặc lỗi client:
     Tác giả hoặc hệ thống chỉ cần gọi lại endpoint `/sync` kèm `txHash`. Backend tự động
     đối chiếu receipt on-chain, trích xuất sự kiện `CopyrightRegistered` và cập nhật SQL Server
     mà không cần phát lại giao dịch lên blockchain, tránh tốn phí gas và lỗi trùng lặp băm.

4. Chuẩn hóa định dạng băm (Case-Insensitive Parity):
   - SQL Server lưu chuỗi băm chữ hoa (`CHAR(64)`), trong khi Node.js và Web Crypto trả về chữ thường.
   - Hệ thống tự động chuẩn hóa `.toLowerCase().trim()` trước khi chuyển sang `bytes32` (Solidity),
     đảm bảo không bao giờ bị lệch mã băm do khác biệt chữ hoa/thường.
